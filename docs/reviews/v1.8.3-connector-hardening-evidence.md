### Kafka and AMQP

The broker audit passed 128 existing deterministic tests, but reproduced two
uncovered failures with local mocks:

- Kafka's legacy poll-batch commit advances to offset 2 when offset 0 remains
  undecided and only offset 1 has been acknowledged. Generator consumption is
  not proof of completed processing when work is queued. A managed-executor
  handshake and regression are being implemented to disable that fallback
  before the first read while preserving standalone-reader behavior.
- AMQP's consumer thread swallows a consumption exception and closes the
  connection while the reader continues waiting for input indefinitely.
  Failure propagation to the reader is being implemented with a regression.

These are deterministic baseline reproductions; live fault acceptance remains
pending. Their fixes must not be recorded as accepted before post-fix checks.

Initial patches now disable legacy batch commits for executor-managed Kafka
sources before intake, and propagate AMQP consumption errors/cancellation after
queued deliveries drain. Added tests pin zero acknowledgements, out-of-order
completion with a gap, a fully decided frontier, consumer loss/cancellation,
queued-delivery drain and executor construction for one/two thread workers.

Combined connector, executor, microbatching and threaded-worker checks passed
298 tests before the final queued-delivery regression was added; the subsequent
focused AMQP run passed all three selected consumer-loss/drain tests. Ruff on
all six changed Python files and `git diff --check` pass. These are targeted
checks on Python 3.12, not the supported-runtime release gate.

Residual Kafka findings remain open: managed tombstone-only/trailing-tombstone
progress, discarded pending-commit retry state, and reconnect exhaustion after
repeated poll failures. Batch delivery accounting currently identifies units
using file metadata; Kafka metadata has no file unit key, so managed batch
execution needs explicit per-record acknowledgement integration. Disabling
the intake commit prevents premature acknowledgement but does not close that
batch progress/replay requirement. Do not re-enable the unsafe fallback or
claim H183-01 complete on the strength of connector-only regressions.
Kafka batch YAML is currently accepted. A batch can report successful sink
output while its offsets remain uncommitted because no broker unit was
registered; this is an open release blocker for batch progress/result truth,
requiring broker-unit accounting or an explicitly reviewed validation policy.

AMQP publisher confirmation must also be reconciled with routing and message
persistence before declaring its advertised durability tier verified. All
selected real broker faults remain pending.

### SNMP traps and polling pilot

Baseline checks: 109 connector unit tests passed; 60 isolated decode/default
listener tests passed and 15 gated cross-stack tests skipped. The loopback
fixtures required execution outside the sandbox. These checks used Python
3.12; the supported Python >=3.13 runtime still requires verification.

- Default trap listener construction supplies `communities=None`, allowing
  every community. A real BER-encoded legacy v2c trap with a mismatched
  community also decodes successfully. Both paths need the configured
  credential policy enforced and documented.
- Legacy malformed input returns `_raw` and is yielded as normal output.
  Existing v3 equivalence tests also explicitly show encrypted packets become
  `_raw` rather than decoded notifications. Rejecting unsupported legacy v3
  reception requires an explicit compatibility decision, not a claim of
  successful privacy support.
- Valid default-stack v2c/v3 receive tests pass. Wrong-key rejection/recovery,
  sanitized error visibility, large Counter64 exactness and current cross-stack
  repetitions remain pending. Installed `trishul-snmp==0.6.2` already supplies
  community allow-lists and categorized listener drops; no dependency change
  has been justified.
- H183-07 is absent: schema and source require one scalar `host`. Existing
  counter identity includes `source_host`, and scheduler jobs use
  `max_instances=1`. The pilot should preserve single-host YAML and output,
  bound separate target pollers, attribute every multi-target record, retain
  healthy results while reporting failures truthfully, and bound stop/restart.
  Structured per-target outcomes and the ten-IP SFTP acceptance campaign still
  need implementation and evidence.
