# v1.8.0 Wave-2 exit gate: journal persistence via manually provisioned persistent mount

Date: 2026-10-08. Baseline: `release/v1.8.0` at `47aa68d` (images
`local-20261008150112`, built from the branch). Environment: the `tram-dev`
kind cluster (manager + 3 workers, helm upgraded via
`scripts/deploy-kind-tram-dev.sh`).

## Procedure

1. Manual persistent mount: a 100Mi PVC on the default `standard`
   (local-path, RWO) storage class, patched into the `trishul-ram-worker`
   StatefulSet as a plain `volumes`/`volumeMounts` entry at
   `/var/lib/tram/worker` — the exact shape later productized by the V18-07
   chart lane (`existingClaim` mode).
2. A 3010-file SFTP batch pipeline (`journal-persist-test`, legacy delivery
   contract) provided the in-flight workload.

## Findings (all evidence-based, observed live)

1. **Fail-closed without a volume** (expected design, new live proof): the
   worker image has no `/var/lib/tram/worker/`, so the journal fails to open
   at boot — admission closed, `/agent/status` reports the condition, runs
   still execute via the legacy bridge. Corollary finding: the outbox drain
   loop retried the dead journal every 1s with full-traceback ERROR spam —
   no backoff. **Fixed** by the V18-07 drain lane (exponential backoff, cap
   60s, condition logged once per period).
2. **RWO node pinning**: all three worker replicas converged onto the
   volume's node (correct scheduler behavior for a single RWO claim). The
   chart lane's values document this and offer per-replica PVCs (fresh
   installs) or an RWX claim as alternatives.
3. **Persistence across pod deletion** (the gate's core claim): the worker
   pod was deleted mid-run. The journal on the PVC survived with the
   in-flight admission reservation from the *old* session intact, and
   `mark_interrupted_on_boot` flipped it to `interrupted` on the new
   session's boot.
4. **Boot adoption live**: after a manager restart, adoption resolved the
   dead attempt by querying the worker's journal (`interrupted` → terminal,
   intent `aborted`, guard identity-released — log: "Boot adoption:
   terminated attempt from journal").
5. **Live bug found and fixed** (`a88e883`): the worker-loss reap path
   (`mark_active_batch_run_lost`) wrote the FAILED run-history row without
   touching the ledger — the attempt stayed `running`, the guard stayed
   held, and every subsequent trigger claim-LOST (pipeline wedged until a
   manager restart). The fix terminalizes atomically via the same
   identity-checked `_terminalize_attempt` pattern the completion callback
   uses, plus an outbox-wins fence; a second leak (`revert_queued_claim`
   orphaning a dispatching attempt) was fixed in the same lane. Full audit
   table of every failure-marking path in the lane report/commit.
6. **Full recovery**: a third run claimed, dispatched to the restarted
   worker, and completed successfully — fresh admission + completion rows
   in the journal with `acked=1` (outbox delivery confirmed by the manager).

## Disposition

The wave-2 exit gate item — "journal persistence validated via a manually
provisioned persistent mount" — is **satisfied**. The storage-dependent
replay oracle re-verifies at wave 3 per the plan amendment; the V18-07 chart
deliverable (`worker.journal.persistence`) productizes the manual shape
with the fresh-install/upgrade paths documented in `NOTES.txt`.

Dev-cluster state after validation: `tram-dev` runs the
`local-20261008150112` images with the manual sts patch in place (a future
`helm upgrade` overwrites the patch; the chart values supersede it). The
test pipeline `journal-persist-test` and its SFTP files remain in the
cluster for the wave-3 rehearsal.
