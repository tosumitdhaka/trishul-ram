## Rolling worker restart finding

The committed `376aece` candidate passed all **11/11** release checks:
**3,564 tests**, **86.96% coverage**. Those results apply to that candidate,
before the additional rollout correction below.

Live kind deployment exposed a separate authorization failure: the restored
`demo-snmp-localhost-to-sftp-jsonl` scheduled run
`358fcffc-7228-4148-9047-160fd1aa6a7d` at 07:24:30 UTC and disposable verification
run `b78370c4-bd7b-4b31-bc03-1d767f3e35f6` both failed with worker
`/agent/run` HTTP **401**, before processing records. The response refusal reason
was not captured; source inspection identified a restart gap: health only exposed
the stable worker identity, and the manager refreshed handshake secrets only after
a detected unhealthy-to-healthy transition. A short rolling restart can stay
healthy across probes while replacing the worker's process session and secret.

The correction exposes the nonsecret process `session_id` in health, refreshes
changed sessions during successful polling, and blocks dispatch until the observed
session handshake succeeds. Already-selected dispatches also check the pending
refresh after RPC client acquisition and mint authorization under the same local
lock, preventing a token captured before a completed refresh from being sent
afterwards. Peers without the new health field retain their existing compatibility
behavior. Authentication settings and legacy-admission policy are unchanged.

Python 3.13 focused worker pool/server checks: **164 passed** in 7.17 seconds;
Ruff and diff whitespace checks pass. Regressions cover continuously healthy process
replacement, failed refresh with blocked dispatch and retry, older health replies,
refresh while dispatch waits for its client, and a second restart during handshake.
Independent review reproduced and checked both concurrency corrections. A restart
after the local mint boundary can still fail cleanly; there is no automatic replay
or legacy downgrade of that dispatch.
