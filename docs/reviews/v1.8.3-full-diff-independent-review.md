## Findings and dispositions

| Finding | Reproduction and consequence | Correction and disposition |
|---|---|---|
| Critical: broker batch acknowledgements could precede loss of earlier file output | Actual `PipelineExecutor` and `LocalSink`, three Kafka-coordinate records with IDs 0–2, NDJSON append output and constant `output.jsonl` filename: all three records were acknowledged and the run returned success, but the file contained only ID 2. Setting file-safe finalization on every broker record staged and published separate writes; publication reset append bookkeeping and later publication replaced acknowledged contents. | Both batch paths now enable file-safe finalization only for genuine source file metadata. Broker accounting and commit/ack barriers remain separate. `test_batch_broker_append_retains_every_acknowledged_record` covers Kafka/AMQP coordinates, local/SFTP implementations and one/two workers, forcing later writes after the first acknowledgement. Resolved. |
| High: retained Kafka partitions could stop committing after another partition was revoked | Actual `KafkaSource` with assignments A+B then A; A offset 0 was in flight at assignment change. Its old global-epoch completion was ignored while its observed offset remained a permanent barrier. Completing A offset 1 left `observed=[0,1]`, `pending={}`, `completed={}` and out-of-order completion `{1}`. Same-set revoke/reassign was also invisible to assignment-set comparison. | Per-partition ownership epochs preserve uninterrupted partition ownership. A real `ConsumerRebalanceListener` fences revoke/reassign even when the final set is unchanged. Pending commit retries merge only under matching partition ownership. Retained-partition and same-assignment callback regressions pass. Resolved. |
| High: multi-target SNMP completion ownership was not consumed by the source | Executor supplied `_completion_managed` in configuration, but the source tested an unset instance attribute. A failed target raised during iteration before the executor's final sink barrier, risking cancellation of healthy threaded work or unpublished staged output. | The source constructor consumes the flag; the executor checks terminal target failure after healthy work drains and sink commit confirms. Actual executor mixed-target output regressions pass for one/two workers. Resolved. |
| High: batch stop/deadline was not connected to multi-target polling | Poll collection consulted `_run_stop_event` and `_run_deadline`, neither of which the executor supplied. The existing direct `source.stop()` test did not verify real batch run control. | `BaseSource.bind_run_control` supplies the same event/deadline to initial and retry source instances. Poll collection cancels active requests and awaits cleanup. The actual executor cancellation regression passes and reports aborted. Resolved. |
| Critical: single-partition Kafka streams do not acknowledge individual records | Actual executor-built `KafkaSource`, broker metadata with a real string cluster ID, offsets 0–2 from one partition, actual local NDJSON output and stop on the next poll: output contains all three records and the run reports success, but zero broker commits occur for both one/two workers. `_stream_source_unit_key` preferred durable partition identity over record coordinates; the final grouped acknowledgement occurred after the source closed its consumer. | Record coordinates now identify processing units. Bounded flush contributors preserve batch sink writes, and drained source batch boundaries perform shared commit/checkpoint barriers before contributor acknowledgements. Managed Kafka stop retains the consumer for reader-owned tail decisions and close. | High: AMQP prefetch-one stream cannot advance its delivery window | Actual executor-built `AmqpSource`, real local NDJSON sink and an owning-thread Pika callback fixture that permits the next delivery only after acknowledging the current delivery: first output was written by interval flush, but neither one/two-worker runs acknowledged it before requesting the next message. Cohort drain/commit/disposition releases that window. Eight actual-source cases cover prefetch one/three, one/two workers and delivered/filtered input. Channel acknowledgements execute on the owning Pika thread after output verification; the three-delivery window uses one sink write. Resolved. |

authorize them. Conservative flush-level loss attribution cannot mark a cohort
delivered when its applicable output obligation failed.

## Acceptance boundaries

- The original PGW ASN.1 corpus and pinned resource conditions for the historical
  two-worker memory/throughput case remain missing. A generic fixture does not
  close B089 or prove the historical less-than-900-MiB target.
- The ten-target network evidence uses isolated loopback addresses and local
  responders with real SFTP readback. It supports the implemented pilot under
  those conditions; it does not establish production-network capacity.
- Kafka offset-commit uncertainty preserves broker replay ownership and can
  duplicate confirmed sink output. AMQP lost confirmations and ClickHouse lost
  responses also retain documented at-least-once duplicate windows. Confirmed
  sink output does not assert confirmed broker-source progress.
- Outstanding fault campaigns, required repetitions/restarts and every selected
  H183 scenario must have dispositions in the
  [evidence ledger](v1.8.3-connector-hardening-evidence.md) before release closure.
- The guarded ClickHouse outage runner and its three repetition records were
  reviewed. They prove real restart of the named isolated ClickHouse 24.10.2.80
  server, retained buffer retry, and failed threaded source finalization followed
  by exact-content replay. Executor resources were rebuilt in the same Python
  process; this is not evidence of worker process restart or real lost-response
  ambiguity. See [the recorded results](evidence/v1.8.3/clickhouse-outage/summary.json).
- The final full backend coverage run is ongoing at this review snapshot. Its
  eventual result must be recorded separately; focused passing coverage is not
  its substitute.
- All 11 mandatory release checks remain required. Plain `ruff check .` is
  currently affected by reported pre-existing untracked artifact-generator
  errors; excluding those artifacts validates release code but does not make
  the mandatory unmodified command green. Preserve those user artifacts and
  resolve the gate disposition explicitly.
- Versions have not been bumped or aligned, and no release tag or publication
  is approved by this implementation review.
