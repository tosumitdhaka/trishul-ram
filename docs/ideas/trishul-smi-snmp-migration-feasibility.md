# Feasibility: Replacing pysmi/pysnmp with trishul-smi/trishul-snmp (tsmi/tsmp)

**Date:** 2026-09-21
**Status:** Feasibility assessment only — no implementation, no issues, no packaging. Product owner decides next steps.
**Update (2026-09-23):** v1.4.5 shipped the SNMP data-integrity work (GH #32/#33/#35/#36) on **pysnmp**; the migration decision remains open — the blockers named below are unaffected.
**Question:** Can TRAM replace `pysnmp>=7,<8` + `pysmi-lextudio>=1.4,<2.0` + `pyasn1` with the in-house `trishul-smi` (tsmi) and `trishul-snmp` (tsmp) libraries, available on PyPI/GitHub and locally at `../trishul-smi` and `../trishul-snmp`?

**Verdict up front:** **Not as a drop-in replacement today.** Both libraries are well-engineered, well-tested, and empirically verified to interoperate with pysnmp on the wire — but two TRAM-facing feature surfaces are hard blockers (SNMPv1, v3 crypto breadth). A full swap is feasible **only after** those gaps are closed (they are closable — the same owner controls both sides). A connector-level parallel adoption is feasible today for v2c + v3/SHA-256/AES-128 deployments. Notably, the classic motivation for escaping pysnmp ("it's abandoned") **does not hold**: pysnmp 7.1.29 (2026-08-21) and pysmi 2.0.0 (2026-04-26) are actively maintained by the LeXtudio community fork.

## 2. What TRAM actually depends on today [code]

TRAM's SNMP surface is concentrated in four files, all with deferred imports (tram stays importable without the deps):

- `tram/connectors/snmp/source.py` (696 L) — `snmp_trap` source (UDP receiver, raw BER decode via pyasn1 + `pysnmp.proto.api.v2c`, best-effort v1/v2c/v3) and `snmp_poll` source (GET / WALK via `nextCmd`).
- `tram/connectors/snmp/sink.py` (255 L) — `snmp_trap` sink (`sendNotification`, builds sysUpTime.0 + snmpTrapOID.0 varbinds manually to avoid MIB lookup).
- `tram/connectors/snmp/mib_utils.py` (338 L) — MIB view building (`MibBuilder` + `DirMibSource` + `MibViewController`), OID resolution both directions, v3 auth construction, and the **existing compatibility shim layer** (`_resolve_hlapi_callable`, `get_hlapi_asyncio` with v3arch fallback, awaitable-or-iterator result handling, snake_case/camelCase tolerance).
- `tram/core/mib_compiler.py` (276 L) — pysmi compile pipeline (`MibCompiler`, `PySnmpCodeGen`, `FileReader`/`HttpReader` against `https://mibs.pysnmp.com/asn1/@mib@`, `PyFileSearcher`/`StubSearcher`, `PyFileWriter`) producing the `.py` modules in `files/mibs_compiled/` (10 bundled MIBs, generated by pysmi-1.4.3).

Supporting surface: `tram/api/routers/mibs.py` (REST upload/compile/download/serve compiled `.py`), `tram/cli/main.py` (`tram mib compile/download`), `tram/agent/assets.py` (worker syncs compiled `.py` from `/api/mibs/{name}`), Dockerfiles shipping `/mibs` + `/mib-sources`, env config (`TRAM_MIB_DIR` etc.).

**User-facing feature contract** (from `tram/models/pipeline.py:167-206`):

| Feature | TRAM today |
|---|---|
| Versions | `v1`, `v2c`, `v3` (`version: str = "2c"`, mpModel 0/1 + USM) |
| v3 auth | `MD5 \| SHA \| SHA224 \| SHA256 \| SHA384 \| SHA512` |
| v3 priv | `DES \| 3DES \| AES \| AES128 \| AES192 \| AES256` |
| Operations | GET, WALK (nextCmd loop, no bulkCmd, **no SET**) |
| Trap receive | UDP, v1/v2c/v3 best-effort, raw BER decode + `_raw` hex fallback |
| Trap send | trap (and inform machinery via sendNotification) |
| MIB | upload → compile → serve; symbolic↔numeric both directions; bundled corpus |

Tests: `test_snmp_connectors.py` (1051 L, includes a real BER-encoded trap decode test), `test_mib_utils.py`, `test_mib_compiler.py`, `test_api_misc_routers.py`, `test_agent_assets.py`, `tests/integration/test_mib_resolve.py`.

TRAM **does not use**: SET, GETBULK, TCP transport, `NotificationType`, `ObjectIdentity.resolveWithMib` except in `symbolic_to_oid`. That materially shrinks the replacement contract.

## 3. What tsmi/tsmp provide [code]

### trishul-smi 0.4.6 — SMI compiler

- Lark-based SMIv1/SMIv2 parser (auto-dialect), BFS dependency resolver, reader chain (`FileReader`/`HttpReader` with retries+cache/`ZipReader`), outputs **JSON** (primary, with `manifest.json` + `oid_index.json` sidecars) or **pysnmp-compatible `.py`** via a Jinja2 `PysnmpFormatter`.
- Async-first (`MibCompiler.compile()` is async; per-thread Lark parser caches anticipate threadpool bridging).
- 422 tests, zero TODO/FIXME in production code, validated against real corpora (824 compiled artifacts in the repo; Standard + Juniper MIB corpora documented).
- **Caveat [code]:** the pysnmp `.py` formatter is explicitly declared *"best-effort, frozen … will not track pysmi feature changes"* (`trishul_smi/output/pysnmp_fmt.py:1-6`). The JSON path is the maintained one.

### trishul-snmp 0.4.2 — SNMP runtime

- Zero-dependency asyncio runtime: `V2cManager`/`V3Manager` (get/get_next/get_bulk/walk/bulkwalk), `V2cNotifier`/`V3Notifier` (send_trap/send_inform), `V2cNotificationListener`/`V3NotificationListener` (async-iterator receive, auto-ACK informs, v3 engine-discovery probes), `V2cResponder` (read-only simulator), `decode_notification` (offline BER decode), in-tree wire codec (no pyasn1).
- `MibBundle`/`load_bundle` consume **only tsmi-produced JSON** (`_SUPPORTED_PRODUCER = "trishul-smi"`); OID resolution both directions, enum-label rendering, varbind enrichment.
- 353 tests, zero TODO/FIXME, per-session `asyncio.Lock`, explicit open/close lifecycle.
- **Caveats [code]:** committed `coverage.xml` is stale (2026-05-07, from a different path tree; pyproject sets `fail_under = 95`); an untracked 8.3 MB experimental native `_codec.so` sits in the local checkout (pure-Python wire path is live).

### Deliberately out of scope (documented deferrals)

SNMPv1, SET (responder returns NOT_WRITABLE), TCP transport, sync wrappers, pysnmp API-compat shims.

## 4. Reference consumer: trishul-snmp-suite [suite]

`trishul-snmp-suite` 2.0.2 (FastAPI + HTML UI "SNMP lab") is the only existing real-world integration, and it is a **clean, thin one**:

- Pins `trishul-smi==0.4.5` / `trishul-snmp==0.3.1` (note: behind latest 0.4.6/0.4.2 — pin drift inside the same ecosystem [pypi/suite]).
- **v2c only** — no `[v3]` extra installed; tsmp's v3 path has zero production references.
- `RuntimeService` is a textbook adapter: owns responder/manager/notifier/listener lifecycle, one `asyncio.Lock`, serializes library objects to dicts. The suite subclasses `V2cResponder.handle_request` for request logging — a non-invasive extension point.
- Async bridge for compile: `MibCompiler.compile()` run via `asyncio.run` or `ThreadPoolExecutor` when a loop is already running (`backend/app/services/bundles.py:211-221`) — directly reusable pattern for TRAM's APScheduler context.
- Suite-level workarounds worth knowing: a custom `TimestampRule` subclass (lib rule only emits numeric epoch), regex-based classification of terse compile errors, per-operation bundle reload (freshness over throughput — a poller should instead cache one `MibBundle`, as the suite's browser service does).

**Translation to TRAM's shape:** all four mediation primitives (compile→bundle→resolve, periodic walk, trap send, trap listen) are exercised and stable in the suite.

## 5. Empirical verification [live]

All executed 2026-09-21 in isolated venvs; scripts preserved under `/tmp/opencode/tsmi-smoke/`.

### 5.1 tsmp internal roundtrips — ALL PASS

- **tsmi compile from TRAM's raw sources:** `SNMPv2-MIB` + `IF-MIB` (with `IANAifType-MIB` dependency auto-resolved) → JSON artifacts written. TRAM's bundled ASN.1 corpus compiles cleanly.
- **Bundle load + resolve:** `load_bundle()` → `resolve("SNMPv2-MIB::sysDescr")` → `(1,3,6,1,2,1,1,1)`; reverse `lookup("1.3.6.1.2.1.1.1")` → `sysDescr`.
- **v2c GET + WALK** against a local `V2cResponder` (loopback UDP): correct values, walk stops cleanly at subtree end.
- **v2c trap send → listener receive:** full varbind set (sysUpTime.0, snmpTrapOID.0, payload) — tsmp auto-builds the mandatory trap varbinds, which replicates TRAM's manual workaround in `sink.py:178-192` for free.
- **v3 authPriv (SHA-256 + AES-128) trap send → listener receive+decrypt:** works, but only after installing `trishul-snmp[v3]` (ImportError otherwise — clean, explicit failure).
- **SET absent from manager API** — confirmed; TRAM doesn't need it.

### 5.2 Cross-stack wire interop with pysnmp 7.1.29 — the migration-critical tests

- **pysnmp manager GET → tsmp `V2cResponder`:** ✅ `ok=True, SNMPv2-MIB::sysDescr.0 = tsmp responder via interop`.
- **pysnmp v2c trap → tsmp `V2cNotificationListener`:** ✅ decoded fully (sysUpTime, snmpTrapOID=linkDown, payload varbind).
- **pysnmp v1 trap → tsmp listener:** ❌ **silently dropped** — no decode error, no event, nothing surfaced. Direct `decode_notification()` on the captured 68-byte v1 trap raises `ProtocolError: Unsupported PDU tag 0xa4` (v1 Trap-PDU). For a mediation product this is the worst failure mode: data loss without signal.

### 5.3 Crypto suite enumeration (hard evidence)

```
AuthProtocol = [NONE, MD5, SHA1, SHA256]      # no SHA224/SHA384/SHA512
PrivProtocol = [NONE, DES, AES128]             # DES enum exists but _encrypt_des raises ProtocolError
```

### 5.4 Library test suites (run against the local checkouts)

- trishul-snmp: **353 passed in 4.51s**
- trishul-smi: **422 passed in 4.97s** (after installing test-only deps `click`, `pytest-httpx`)

Both green and fast — consistent with the Beta-but-solid codebase reading. (Coverage not re-measured here; the repo's own gate demands 95%.)

## 6. Gap matrix: TRAM contract vs tsmp 0.4.2

| TRAM requirement | tsmp status | Verdict |
|---|---|---|
| SNMPv2c GET / WALK | `get`/`get_next`/`walk`/`bulkwalk` | ✅ verified live |
| v1 community polling (`version: "1"`, mpModel=0) | not implemented (deferred) | ❌ **blocker** |
| v1 trap reception | PDU tag rejected; **silently dropped** on the listener path | ❌ **blocker** (data loss w/o signal) |
| v3 USM auth MD5/SHA | `AuthProtocol.MD5/SHA1` | ✅ |
| v3 auth SHA224/SHA384/SHA512 | absent | ❌ regression vs `pipeline.py:202` |
| v3 priv AES128 | `PrivProtocol.AES128` | ✅ verified live |
| v3 priv DES/3DES/AES192/AES256 | absent; **DES raises ProtocolError** despite enum presence | ❌ regression vs `pipeline.py:204` |
| Trap/inform send | `send_trap`/`send_inform` | ✅ verified live + cross-stack |
| Trap receive (raw BER decode) | `decode_notification` + listeners | ✅ v2c/v3; ❌ v1 |
| SET | absent | ✅ TRAM doesn't use it |
| GETBULK / TCP | get_bulk exists; TCP absent | ✅ TRAM doesn't use either |
| Timeouts/retries per target | constructor params | ✅ |
| MIB view (numeric↔symbolic) | `MibBundle.resolve/lookup` over tsmi JSON | ✅ verified live |
| MIB compile (pysmi pipeline) | tsmi `MibCompiler` (async, different API) | ✅ equivalent-in-spirit; API rewrite needed |
| Engine lifecycle | session open/close vs `SnmpEngine` per op | ✅ `mib_utils` already abstracts this |
| pyasn1 BER | in-tree wire codec | ✅ verified live |
| pysnmp `.py` MIB corpus (`files/mibs_compiled/`) | tsmi `pysnmp` format exists but is **frozen**; JSON is the maintained path | ⚠️ corpus must be recompiled to JSON (verified working on TRAM's raw sources) |

**Structural (non-blocking but real) differences:** no `SnmpEngine`/`ObjectIdentity`/`ObjectType`/`UdpTransportTarget` API shapes — TRAM's `mib_utils.py` would grow a tsmp adapter alongside the existing 6.x/7.x + camelCase/snake_case shims. The suite's `RuntimeService` proves this adapter is thin.

## 7. Risk register

1. **Bus factor / validation** [pypi]: both libraries are single-owner Betas with ~4 months of history and near-zero external adoption. Mitigating factor: the owner is also TRAM's owner, and the suite + 775 passing tests + this assessment's live tests are real validation.
2. **Counter-motivation** [pypi]: pysnmp is *not* dying — 7.1.29 shipped 2026-08-21. The swap's justification must be the genuine wins (clean asyncio API, zero pyasn1, no 6.x/7.x dual-compat shims, better error messages, ownership of the SNMP stack), not abandonment fear.
3. **Silent v1 drop** [live]: the failure mode is invisible data loss; any adoption must either fence v1 configs or add explicit rejection.
4. **Frozen `.py` formatter** [code]: if TRAM keeps a pysnmp runtime anywhere, tsmi cannot be its compiler long-term.
5. **Stale coverage evidence** [code]: re-verify the 95% gate on the current tree before depending on it.
6. **Pin discipline** [suite]: the suite already lags (0.3.1 vs 0.4.2) — a mono-ecosystem drift pattern to guard against if TRAM adopts.

## 8. Options

### Option A — Full replacement now
**Blocked.** `version: "1"` support and the v1/v3-crypto breadth are user-facing TRAM contract items; a swap today is a feature regression for exactly the legacy-telecom segment a mediator must serve. Proceeding would require TRAM to formally deprecate v1 and DES/3DES/AES192/256/SHA2-384/512 configs first — a product decision, not an engineering one.

### Option B — Parallel connector behind a flag (feasible today)
New connector implementations (e.g. `snmp_poll2` / or a `stack: trishul` option) using tsmp for **v2c and v3/SHA-256/AES-128** pipelines, keeping the pysnmp stack for everything else.
- Effort: ~1 week (adapter in `mib_utils`, two thin connector paths, compile pipeline via the suite's threadpool-bridge pattern, tests). The tsmp stack would also carry the trap sink/listener for those pipelines.
- Value: real-world soak of tsmp inside TRAM at production load, at controllable blast radius; cross-stack interop is already proven (§5.2).
- Caveat: two SNMP stacks shipped simultaneously = dependency bloat for `tram[snmp]` users; MIB corpus must be dual-format during the transition or JSON-only with `resolve_oids` handled per stack.

### Option C — Close the gaps in tsmp, then swap (recommended sequence if the goal is full replacement)
The decisive fact: **the owner of the gap is also the owner of TRAM.** The blockers are documented deferrals, not architectural walls:
1. SNMPv1 community polling + v1 trap decode (PDU tag 0xa4; also fix the silent drop → raise/log explicitly). Precedent: the v3 listener work landed recently; v1 is on the roadmap's deferred list, not a rejection.
2. USM crypto breadth: SHA-224/384/512, AES-192/256, 3DES (or explicitly DES/3DES-desupported with TRAM config validation updated to match).
3. Optionally: a `coverage` re-run + `cached` compile-status wiring the suite noticed missing.
Then execute the TRAM migration: `mib_utils` tsmp adapter, `_decode_trap` → `decode_notification`, `mib_compiler` → tsmi (async bridge), `files/mibs_compiled/` → JSON bundles (compile path verified on TRAM's own raw sources), `routers/mibs` + `agent/assets` serve JSON, rewrite the SNMP/MIB test suites.
- Effort after parity: **~2–3 weeks** in TRAM (4 core files + router/CLI/assets + ~1500 lines of tests), behind a feature flag per the TRAM_STREAM_SINGLE_PLACEMENT precedent.

### Option D — Adopt tsmi only (keep pysnmp runtime)
Adopt tsmi as the MIB compiler while pysnmp stays the wire runtime. **Low value / awkward**: the maintained tsmi output is JSON (only tsmp reads it), the `.py` output TRAM would need is the frozen formatter, and pysmi-lextudio already works. Not recommended.

## 9. Recommendation

1. **Do not full-swap now** (Option A blocked on v1 + crypto breadth).
2. If the goal is eventual elimination of pysnmp/pysmi: **Option C** — land v1 + crypto parity in trishul-snmp first (user-owned, documented deferrals), then migrate TRAM behind a feature flag. The empirical groundwork is already positive: both libs' suites are green, TRAM's MIB corpus compiles with tsmi, and cross-stack wire interop with pysnmp is proven.
3. If the goal is early production validation rather than migration: **Option B** at ~1 week, fenced to v2c + v3/AES-128 pipelines with explicit config-time rejection of v1 and unsupported crypto (never silent).
4. Independent of any adoption: fix in tsmp the **silent v1-trap drop** (log/raise instead of ignoring) — as a mediation-grade library, data loss without signal is the one finding here that is a defect regardless of TRAM's plans.

## 12. Addendum — v0.5.1 re-validation (2026-09-25)

Upstream v0.5.0/v0.5.1 closed both hard blockers (#8 SNMPv1, #10 USM crypto parity). A full harness re-run (tsmi/tsmp 0.5.1 + pysnmp 7.1.29, live wire; scripts, per-check JSON, and the root-cause debug chain preserved under `/tmp/opencode/tsmi-smoke-v05/`, `REPORT.md`) verified:

**Green:** lib suites (650 + 571 passed) · MIB compile of the TRAM corpus (15 raw MIBs → JSON + manifest, re-run emits the cached status per tsmi #15) · SNMPv1 GET/GETNEXT/WALK + v1 trap send/receive + `decode_notification` · v2c GET/WALK/trap · v3 MD5/SHA-1 both directions on the wire · the full SHA-224/384/512 × AES-192/256/3DES matrix in-stack · walk boundaries (bulk + GETNEXT-loop, gap crossing, EndOfMibView) · cross-stack interop with pysnmp 7.1.29 (GET + v2c trap, both directions) · silent-drop counters (#9 fix verified live).

**One blocking defect (new, wire-proven):** tsmp truncates every USM HMAC to 12 bytes (`_AUTH_TAG_LEN = 12`, `security/usm.py:28`; its suite pins this in `test_sha2_auth_tag_is_12_bytes`) while RFC 7860 requires 16/24/32/48-byte authParameters for SHA-224/256/384/512. All 17 SHA-2 × priv combinations were rejected by pysnmp and net-snmp snmpd (`usmStatsWrongDigests`), and the tsmp listener drops standard-compliant SHA-2 traps. Root cause isolated to the tag length — a rebuilt request with a correct 24-byte SHA-256 tag is accepted and decrypts cleanly (key derivation, localization, Reeder/3DES priv, and engine discovery are all RFC-correct). Upstream missed it because its cross-agent CI runs v2c-only. DES-CBC (#11) remains fail-fast unimplemented. Filed upstream as [trishul-snmp #28](https://github.com/tosumitdhaka/trishul-snmp/issues/28).

**Verdict:** NO-GO for option C as of 0.5.1 — one upstream fix away from GO at the original ~2–3 week estimate. Maintainer decision (2026-09-25): option C scheduled for v1.5.0 behind a feature flag (GH #72), gated on the upstream fix + a green harness re-run.
