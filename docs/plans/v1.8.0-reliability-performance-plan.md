## Release objective and scope

Resolve all R1–R16 findings in v1.8.0. The release must make execution ownership
recoverable, completion truthful, source acknowledgement follow a decided
delivery outcome, administrative operations stop or drain actual execution, and
capacity remain bounded under slow dependencies. Correctness is the prerequisite
for performance claims.

This is one minor release with staged implementation PRs and one final release
PR collecting the evidence. No finding in the coverage table is deferred. A wave
is complete only when its implementation, tests, compatibility changes, docs,
and review disposition are complete. Dates follow completed gates rather than
forcing a release around unfinished ownership or delivery changes.

Keep the thread-based execution model and single manager deployment. Arbitrary
external sinks cannot provide universal exactly-once delivery; crash replay can
duplicate acknowledged writes. v1.8.0 provides controlled at-least-once behavior
where the source is replayable and the sink supports confirmed delivery. It
must report intentional drops, partial delivery, and uncertain outcomes honestly.
Broker reassignment can duplicate external writes when an old consumer retains
in-flight work; that limit is separate from manager replacement ownership.
Manager HA, deeper manual queues, new connectors, and a durable webhook service
are separate features. Their absence must not be presented as a v1.8.0 guarantee.

## Mandatory invariants

1. **Ownership:** one active batch attempt per pipeline; one active stream
   attempt per placement slot. Dispatch-in-flight, stopping, and unknown attempts
   retain that guard. A pending request has a separate queue reservation and may
   coexist with one active attempt; it acquires the execution guard only at claim.
   Config changes do not release execution ownership.
2. **Identity:** logical `run_id`, execution `attempt_id`, pipeline generation,
   slot identity, and worker boot/session ID accompany every dispatch, state
   update, status observation, cancellation, and completion.
3. **Delivery:** source acknowledgement/destructive finalization follows every
   applicable obligation: confirmed emitted output, durable retained state, and
   recorded filter/DLQ/explicit drop disposition. These obligations are conjunctive;
   retained state cannot replace confirmation of already emitted output. Abort,
   exhausted retry, and failed DLQ never acknowledge an undecided unit.
4. **Truthful results:** buffered acceptance is not delivered output; a failed
   commit/publish cannot produce clean success. Filtered records are distinct
   from failed/dropped records. Partial fan-out has per-sink outcomes.
5. **Uncertainty:** transport timeout is `unknown`, not evidence of worker death
   or dispatch rejection. Unknown ownership is not eligible for blind redispatch.
6. **Cancellation:** stop/restart/update/delete have observable asynchronous
   completion and one deadline. The replacement cannot write while an unfenced
   previous attempt can still write. Terminal audit survives pipeline deletion.
7. **Bounded work:** every admission queue, source bridge, record buffer,
   outbox, error sample store, and RPC fan-out has a count/byte/concurrency limit.
   Undelivered durable outcomes are never evicted to satisfy retention limits.
8. **Recovery:** restore desired state and execution ownership before opening
   scheduled dispatch. Every accepted request has a resolvable run ID until its
   documented audit retention expires.

## Design decisions to implement

### A. Durable manager execution ledger

Add versioned migrations for both supported persistence dialects: SQLite and
PostgreSQL. Use database transactions and conditional updates, not an in-memory
lock as the durable claim. Keep legacy history and placements readable during
the migration; do not introduce multiple active managers in this release.

The ledger owns:

- Pipeline desired state (`running`/`stopped`), config generation and version,
  schedule metadata, and deletion tombstone. Desired state is separate from
  observed pipeline status and explicit manual-run permission.
- Logical run intents: run ID, origin, accepted request fields including
  `flush`, requested/expiry times, requested config reference, claimed dispatch
  snapshot/generation/schedule type, and final logical outcome.
- Attempts: attempt ID, worker ID and session, slot, dispatch timestamps,
  uncertainty/cancel reason, current state, and execution fence token.
- Active execution guards: one transactional row per batch pipeline or stream
  slot. Acquisition, transition, release, and completion all compare identity.
- Committed delivery/checkpoint units: source identity/position frontier,
  per-sink result, state revision, and completion receipt needed for recovery.

Attempt states: `claimed → dispatching → running → stopping → terminal`;
`unknown` can be entered from dispatching/running/stopping when evidence is
insufficient. Confirmed rejection releases the guard; transport uncertainty
does not. A terminal attempt has an immutable result. Retries create new attempt
IDs under the same logical run ID; diagnostics retain actual work per attempt.
Within-attempt processing/commit retries keep the same attempt and uninterrupted
guard; only ledger-authorized replacement creates another attempt.
The V18-01 state diagram must enumerate the exits from `unknown`, not only its
entries: terminal via completed-journal query/lost-run resolution, terminal via
durable revocation plus quiescence, and retention under operator hold with a
surfaced action. A `claimed` attempt that never reached dispatch before a
manager crash is resolvable locally: no dispatch occurred, it is never
`unknown`, and it cannot collide with a replacement.

Worker/manager compatibility must use an explicit protocol version and capability
set. A v1.8 manager does not assume a legacy worker understands fencing, commit
receipts, admission limits, or durable completion. Strict v1.8 execution requires
those capabilities; a rolling-upgrade bridge is for draining existing work.

### B. Worker journal and durable completion

Add a small worker journal using Python's standard-library SQLite, preserving
the worker image's independence from SQLAlchemy/APScheduler. Store it under a
dedicated persistent `worker.state` mount, separate from the ephemeral asset
cache. Use WAL, verified durability settings, file permissions, and a bounded
storage budget. Fail readiness/admission if the configured durable journal is
unavailable, corrupt, or full; preserve recoverable rows for diagnosis.

Cancellation/revocation atomically persists an admission tombstone even when
the attempt has not arrived or been reserved. Dispatch checks that tombstone
in the same transaction as reservation; a delayed revoked POST cannot start.
An absent-attempt query/404 is not revocation or proof of quiescence.

Atomic journal reservation precedes thread creation. Repeating an active or
completed attempt returns its existing acceptance/result, not HTTP 409 treated
as a new failure and not another thread. Conflicting identity is rejected.
On restart, unfinished attempts are reported as interrupted/uncertain and are
not silently re-executed before the manager resolves ownership.

Write completion locally before removing execution from active tracking. A
bounded outbox retries until the manager durably acknowledges the same attempt
and result. Add an internal query/replay endpoint so reconciliation can recover
completed outcomes. Journal cleanup retains undelivered results and idempotency
tombstones. Separate audit retention, start-authorization validity, and completion
replay retention. New dispatch requires a manager-authenticated bounded-lived
start authorization bound to run/attempt, generation, slot, and worker session,
with issued/expiry times and a fixed maximum TTL/skew. Reject old sessions,
future-issued or expired authorizations, and TTLs beyond the configured maximum.
Known accepted attempts return existing state/results even after authorization
expiry; expiry never stops active work or discards an undelivered completion.

Persist a rejection watermark including every clock observation used for admission
and authorization/tombstone GC. GC advances it durably in the same transaction
before deleting identity rows; an idle journal cannot retain an old validation
watermark while deleting newer expired identities. A clock rollback beyond
permitted skew fails new admission closed until trusted time is restored; restart
cannot reset the watermark. Trusted-time recovery cannot lower/reset it while
authorizations from the affected session remain admissible. Recovery from an
erroneous forward clock jump requiring a lower clock first invalidates the whole
old start-authorization/session epoch, preserving execution ownership and known
active/undelivered results for query/recovery. GC of revoked/completed idempotency
rows waits until all possible valid authorizations expire plus skew.
After GC, validation still rejects the expired token; retrying a retired attempt
cannot create a thread. The manager never reissues authorization for a retired
identity; replacements always use a new attempt ID. Freeze TTL, skew, token
verification/key-rotation rules, and trusted-time recovery in V18-01. Enforcement
is local even when the manager is unreachable; journal/PVC loss requires a new
worker session and operator recovery, never silent admission of old tokens.
Admission checks leave disk headroom for active attempts to record completion
even when new work is rejected.
V18-01 also records a fallback simplification for this machinery: an
epoch-scoped minimum-valid-time row with a fail-closed operator reset satisfies
the same requirements with a smaller clock-arithmetic surface. The watermark
design above stays primary; the fallback is the first simplification lever if
implementation shows the complexity is not worth it.

A crash after an external sink write but before its receipt/checkpoint is
durable remains an uncertain outcome. Recovery may replay after ownership is
resolved and can duplicate that write; the journal does not claim to eliminate
this window.

### C. Delivery receipts, sink commits, and source acknowledgement

Extend plugin interfaces compatibly with capabilities and explicit commit/error
hooks. Separate resource `close()` from a delivery `flush/commit` barrier.
Capability declarations name the confirmation tier (e.g. fsynced local output,
remote durable acceptance, or weaker remote acceptance); synchronous return alone
is not proof of durability. Default adapters are permitted for audited built-in
sinks with a defined confirmation tier; buffered
or background-writing sinks must implement the barrier and surface latched
errors. Audit all built-in sinks for these behaviors, not only ClickHouse.
An unknown custom plugin cannot silently claim replay-safe delivery; document
its capability declaration and reject strict combinations when it is absent.

Track each logical source unit (file, broker delivery, Kafka poll/partition
frontier) and its matched sink obligations. Retain bounded pending receipts until
the unit's delivery decision is durable. Required sinks are all matched sinks
unless a pipeline explicitly selects a documented alternative. Filtering is
successful intentional non-delivery; `on_error: continue` creates a visible
partial/drop outcome, rather than clean success for failed records.

Error policies:

| Policy | Executor behavior | Source disposition |
|---|---|---|
| `abort` | Signal supervisor, stop new intake, retain failure and confirmed partial writes | Do not acknowledge undecided units; leave input for replay |
| `retry` | Retry retryable processing/commit failures within configured count/deadline; permanent failures terminate; distinguish sink retry from unit/run retry | Acknowledge only a completed disposition; retain stable logical run ID |
| `continue` | Continue intake with explicit per-record/per-sink loss accounting and partial terminal outcome | A drop is acknowledged only under this explicit policy |
| `dlq` | Commit the failed unit to the configured DLQ or an explicitly supported persistent fallback spool; surface buffered/background failures | Ack only after durable DLQ/spool receipt; otherwise pause/stop and leave input unacknowledged |

DLQ receipts distinguish delivered-to-DLQ, fallback-spooled, failed-DLQ, and
intentional drop counters/status. Fallback spool uses atomic publication and
file/directory fsync before receipt, a dedicated persistent mount, and quota
headroom. Destination failure plus unavailable/full/failed spool is a failed
disposition, never a DLQ success. Replay/dedup identity and recovery of spool
entries are explicit; a nonreplayable source reports unrecoverable loss honestly.

An explicit continue policy does not authorize destroying input after an
uncertain file-publication failure. Preserve the source unit for repair/replay.
Represent `partial` in run history/API/UI; keep success for fully decided
non-error delivery/filter outcomes. Existing clients receive an API migration
note and exhaustive examples for new status values.

ClickHouse retains rows until confirmed insert, serializes timer/foreground/close
flushes, latches background errors, and uses a commit barrier before source
acknowledgement or final result. Cancellation cannot erase its pending buffer.
AMQP retains tags until disposition, marshals ack/nack onto the connection's
thread, and uses broker prefetch for backpressure. Cover connection loss while
acknowledging and duplicate/redelivered tags. The channel/session-scoped tag is
only an acknowledgement handle; it is not a durable redelivery identity.

Kafka commits explicit per-partition completed frontiers. Threaded execution
must not commit past queued/in-flight records; completion order is independent
of read order. Until that implementation passes broker tests, reject strict
Kafka delivery with `thread_workers > 1` instead of advertising a guarantee
the path cannot provide. Do not use the timer flusher as an independent owner
of acknowledgements. Bind intake, receipts, checkpoint, and explicit eligible
offset commits to consumer session and partition-assignment epoch. Revocation
stops intake and prevents old-epoch completions advancing a new assignment;
commits run on the owning consumer. Bound revoke drain and report unresolved
writes, tombstones, and partitions with no payload records. Test stale commit
responses and consumer expiry during blocked writes. Broker offset fencing
cannot prevent duplicate external writes when old work survives reassignment.

For file outputs, all sink commit/publish hooks complete before processed-file
mark/move/delete. Sequential, incremental, threaded, stream file-unit, and
Protobuf passthrough paths share this protocol. Publish is idempotent; failed
rename retains input and recoverable staged targets. Account for rolling
multiple parts, multiple sinks, partial publish, retry, and `batch_size` stops.
Persist a publication manifest for all rolling parts and stable target identities;
recovery resumes partial publication without truncating confirmed output. An
incomplete source file at a `batch_size` boundary is never marked done/deleted.

#### Replay identity and atomic state checkpoints

Freeze a connector capability matrix before enabling durable retained state:

| Source | Persistent replay identity | Required boundary |
|---|---|---|
| Kafka | Cluster/topic incarnation, partition, offset | Consumer session/assignment epoch additionally fences acknowledgements |
| AMQP | Verified stable producer message ID within a documented uniqueness namespace | Channel/session delivery tag remains a separate ack handle; body hashes cannot distinguish identical legitimate messages |
| Local/SFTP files | Immutable file version or documented content fingerprint plus source namespace and unit position | Detect same-path replacement; pathname alone is insufficient |
| Other sources | Explicit connector capability declaration | Reject strict stateful retention without adequate identity, or require an explicit weaker repeated-contribution contract |

Persist source-unit disposition/frontier, transform revision/blob, and required
sink outcomes in **one authoritative atomic manager DB transaction** (local DB
in standalone mode). Worker journal/outbox carries the same immutable transaction
identity/receipt; it cannot independently authorize source acknowledgement before
the authoritative commit. All applicable obligations must be satisfied together:
confirmed emitted output, durable open-window retention, and recorded filtering,
DLQ, or explicitly authorized drop. Failure/timeout leaves the unit pending until
query resolves the transaction; no frontier or state can advance separately.

After a committed checkpoint, an acknowledgement failure/lost response causes
replay to recognize the stable unit ID, restore committed state, and retry
acknowledgement without reapplying transforms or re-emitting recorded outputs.
State writes compare execution generation and revision and reject stale writers.
Failure to load/save required state pauses/fails the attempt. External output
and DB state are not globally transactional: a crash after output but before
checkpoint can duplicate output; document sink deduplication options and this
remaining window.

Config changes with open retained windows require an explicit compatible-state
migration, drain/flush, preservation, or operator-approved reset/loss disposition
before generation switch. Never silently discard acknowledged retained windows
on fingerprint mismatch. Preserve the existing stateful broadcast restriction;
partitioned state ownership across broadcast slots is outside v1.8.0.

### D. Liveness, recovery, and scheduling

Take one bounded status snapshot per worker per reconciliation pass and classify
each observation as active, confirmed absent, or unknown. A timeout/malformed
reply cannot synthesize terminal failure. Completed-journal query precedes any
lost-run synthesis; loss and completion both conditionally update the exact
attempt/generation. Late/duplicate callbacks record only their own attempt and
cannot clear a newer guard or change another generation's status.

For uncertain/in-flight dispatch, release ownership only after authoritative
rejection, durable admission revocation plus quiescence, or actual process
termination/write fencing. A delayed POST must remain unable to start after the
guard is released. For accepted execution, require durable cancellation plus
quiescence, a confirmed terminated worker process/session, or an infrastructure
fence that actually prevents its writes. A health timeout, lease expiry, force
deleting a Kubernetes pod, or a node partition alone is not such proof. If proof
is unavailable, retain `unknown` and surface an operator action. New lease/fence
tokens protect manager-mediated state; generic external sinks do not honor them.

Persist stream intent and empty placement slots even if no worker accepts initial
dispatch. Recover enabled streams from capacity/transient errors using bounded
jittered backoff; permanent validation errors remain visible. Worker health/session
reports exist independently of per-run stats. Reproduce the v1.7 worker-rollout
gap from the evidence rather than assuming the roadmap's suspected cause.

Boot order: DB and schema ready → worker sessions/status/journal snapshot →
ledger/queue/placement adoption → conditional recovery → scheduler dispatch →
readiness. Unreachable ownership can remain visible as unknown while unaffected
pipelines operate; it cannot be replaced blindly. Manager mode requires a DB;
standalone ephemeral mode must be explicitly configured, with reduced guarantees.

Keep UTC scheduling and the one-pending-manual-run policy. Make coalescing,
misfire grace, overlap skip/defer, and downtime behavior explicit in the model,
API, metrics, and docs. Defaults match current UTC/coalesced/skipped behavior;
no automatic historical-window backfill in this release. Every skipped/deferred
scheduled occurrence has observable accounting. The active guard applies to
both APScheduler and manual execution, not two independent executor queues.

Queued request semantics: retain immutable accepted request fields and requested
config reference; claim the latest compatible config atomically with its actual
YAML, generation, schedule type, and `flush` flag. Updates may refresh only
unclaimed queued dispatch snapshots. Changing to an incompatible schedule/source
terminates the pending request with a reason; never reinterpret it as a stream.
Stop/delete/expiry create durable aborted/failed outcomes under the returned run
ID. Queue expiry runs independently of long liveness scans. Explicit manual
execution of a stopped/disabled batch remains supported; a later stop rescinds
its pending request.

### E. Cancellation and shutdown

Use explicit Uvicorn server objects and main-thread signal supervision for both
worker servers. Add worker admission/draining state and a machine-authenticated
drain API surfaced through the manager. SIGTERM and explicit drain use the same
state machine; a listener failure terminates its sibling through that supervisor.

One monotonic deadline covers intake stop, source unblock, chunk processing,
sink commit, checkpoint, journal completion, callback acknowledgement when
available, and server joins. Pass cancellation/deadlines to batch and stream
executors and every source adapter. Audit idle reads, reconnect waits, native
I/O timeouts, retry sleeps, and outstanding futures. Python cannot safely kill
an arbitrary blocked thread; an uncooperative adapter retains its ownership
guard and reports deadline exceeded, then process termination/recovery resolves
it. Never start its replacement just because a thread join timed out.

Stop means stop new scheduling and request cancellation of active work; reply
202 with the operation/run identity until quiescence. Restart/update record the
new desired generation and start it only after old execution releases ownership.
Delete tombstones the pipeline, cancels/drains executions, preserves audit and
checkpoints needed to finish recovery, and performs final cleanup after quiescence.
Manual and APScheduler pools share this admission/drain protocol. Manager shutdown
may leave healthy remote workers executing; persist their claims and keep
completion replay available after manager restart.

### F. Capacity and control-plane performance

Use worker-enforced batch/stream slot limits plus manager reservations held during
HTTP dispatch, including unknown outcomes. Report slot capacity, queue pressure,
recent CPU/memory signals where available, and worker session/drain status.
Fallback selection uses consistent slot units; recent throughput deltas are a
secondary signal, never lifetime-average bytes mixed with arbitrary run weights.
Tie-breaking is round-robin/fair. No capacity returns a retryable admission
response or durable manual queue entry; healthy-but-full is not worker failure.

Bound source bridges and executor buffers by bytes and count. Also bound
transform key/window cardinality and resident state bytes before allocation,
including counter baselines and open windows. Overflow pauses/backpressures or
fails with an undecided source unit; it never silently evicts required un-emitted
state. Disk checkpoint limits alone do not bound transform memory. For replayable
brokers block/pause intake instead of acknowledging early. For non-replayable
UDP/NATS Core/MQTT configurations, define counted drop or connection-pause policy
and publish the actual guarantees; do not claim broker persistence that is absent.
Webhook 202 remains acceptance into a bounded in-memory queue; bound queued bytes
and concurrent body reads, preserve 413/503 behavior, and document pod-loss risk.

Offload synchronous controller/DB/network calls from async API handlers using a
bounded dedicated executor. Refactor lifecycle mutations into
claim → network work → identity-checked commit, with cancellation/compensation
for dispatch accepted after its intent was removed. No network I/O under the
global lifecycle lock. Pool worker RPC/REST sink clients and the parallel-sink
executor; set connect/read/write/pool deadlines and maximum concurrency.

Batch telemetry per worker, independently of execution progress. Cap and evict
stale stats and error samples. Count total errors while keeping bounded examples.
Incremental retention jobs prune only eligible terminal history, placements,
checkpoint receipts, and journal tombstones; preserve active/unknown/undelivered
rows and processed-file identities unless a safe dedup-retention policy is
explicitly selected. Durable DLQ/spool quotas cannot silently discard failures.

days before contingency, so treat the stated top end as optimistic; section
B's authorization/watermark machinery is the first simplification candidate if
the envelope must be held. This is approximately 16–31 working weeks including
contingency, not a committed date. Add staffing only after interfaces are
fixed; integration and review remain work.

Merge-serialize changes to `executor.py` (delivery/retry/state/file),
`controller.py`/`db.py` (ledger/queue/recovery/lifecycle), `agent/server.py`
(protocol/journal/drain/telemetry), `connectors/file_sink_common.py`
(publication manifests and DLQ-spool atomic publication share its helpers),
and `api/routers/internal.py` (identity-checked completion and management
offload both touch its routes). Separate connector implementations can proceed
against frozen contracts; do not have competing controller or executor rewrites.
Minimal module extraction into delivery, execution-ledger, journal, and admission
components is part of these packages; a broad unrelated refactor is not.

Fast corrective PRs may land while the release is assembled, but a partial wave
is not evidence that v1.8.0 resolves the review. Each PR carries package IDs,
fault tests, API/config/doc changes, and review disposition. New flags may stage
protocol rollout; no production switch restores known false-success behavior.

### Upgrade and rollback gates

### Quantitative acceptance

Freeze machine/image/Python/CPU/memory profiles and repeat v1.7 controls on the
same quiet host. Existing corrected v1.6 and v1.7 pilot reports guide workload
selection; they are not v1.8 baseline measurements. Use at least five paired
repetitions, a 60-second warmup and at least ten minutes of steady state for
streams. Batch profiles run long enough to avoid 0.3-second timing quantization.
Report confidence intervals, offered/accepted/durable rates, partial/drop/replay
counts, p95/p99 delivery and RPC latency, RSS, CPU seconds per delivered record,
throttling, queue bytes/age, and reconcile duration.

Proposed release gates, calibrated and fixed in Wave 0 using the reference
profile (not silently relaxed after an implementation misses):

- Zero false clean success, wrong-attempt mutation, acknowledged-undecided unit,
  or concurrently unfenced replacement in the deterministic and fault matrices.
  Replay duplicates are measured and reported; zero universal duplicates is not
  the acceptance contract.
- Reference worker shutdown: admission/readiness changes within 1 second;
  cooperative drain completes within 30 seconds with a 45-second pod grace.
  Injected uncooperative I/O produces explicit deadline/unknown state, not false
  success or unsafe replacement.
- Reference recovery: reachable-session initial stream recovery and restart
  adoption within 30 seconds after dependencies/capacity are healthy. Unknown
  partition cases are excluded from that liveness target and must surface within
  one bounded reconciliation pass with a documented operator path.
- At 1000 active/synthetic run observations across 10 workers, reconcile RPC
  count is O(workers), pass p95 ≤5 seconds with healthy reference endpoints;
  queue expiry is processed within 5 seconds of its deadline despite unavailable
  status endpoints. A status sweep budget is ≤5 seconds, with unknown results
  for unfinished probes. Release evidence must include timeouts, not just fast
  mocks.
- Management event-loop lag p99 ≤50 ms and liveness p99 ≤250 ms during slow
  worker/Kubernetes calls on the reference control-plane profile. Event-loop
  lag is measured by an asyncio watchdog task sampling `loop.time()` drift,
  frozen with the Wave 0 campaign spec so the gate is reproducible.
  Saturating the bounded management executor returns explicit retryable
  overload responses.
- Broker/webhook/UDP bridge budgets are demonstrably enforced under a ten-minute
  slow-sink flood. RSS plateaus within the configured budget plus measured fixed
  overhead and stays below 80% of the selected pod limit; reject configurations
  whose budgets cannot fit that limit. No OOM-based admission policy.
- On unchanged synchronous delivery workloads, sustainable durable throughput
  regression ≤10% and p95 completion-latency regression ≤10% at matched offered
  rate. Measure journal/commit overhead separately. Workloads previously gaining
  speed by early acknowledgement or nondurable buffering are judged on the new
  durable contract, with costs documented rather than hidden as a regression.
- Use the finite campaign below to cover 500m/1CPU/2CPU, 1/3/10 workers,
  low/high client concurrency, and 10/100/1000 pipeline counts. Separate
  single-batch throughput from fleet concurrency. No blanket speedup promise.

### Finite benchmark campaign and machine-time budget

Wave 0 freezes a table of exact inputs, durable contracts, machine profiles, and
offered rates. These are selected cells, not a Cartesian product of every axis:

| Campaign | Cells | Profiles and purpose |
|---|---|---|
| Paired v1.7/v1.8 controls | 8 | JSON short/deep chains (2), file→file serial/threaded (2), eligible Protobuf (1), webhook (1), Kafka→local (1), AMQP→synchronous sink (1); default 1CPU/one worker, matched confirmation tier; any incomparable control is reported separately |
| New delivery contract | 4 | Kafka→ClickHouse, AMQP→buffered sink, stateful replay, durable file publication; measure committed rates and durability overhead without applying the unchanged-contract regression gate |
| Synthetic reconciliation | 6 | 10/100/1000 observations at 1 and 10 workers, including slow/failed endpoints; validate O(workers) probes and independent queue expiry |
| Capacity sweeps | 6 | 500m/1CPU/2CPU at 1 and 3 workers, low/high client concurrency stepped within each cell; count accepted/completed/queued outcomes and measure fairness |

At five repetitions and 11 minutes per stream cell, paired controls plus new
contract cells require approximately 18.3 machine-hours. Reserve another 8–16
hours for batch sizing, capacity/reconcile sweeps and setup, and 12–24 hours for
broker/kind fault and upgrade rehearsals: roughly 40–60 machine-hours per full
campaign before debugging reruns. This is automated runtime, separate from the
engineering estimate. Reuse images/fixtures; schedule campaigns on isolated
hosts. Contract failures are release blockers even if performance is acceptable.
