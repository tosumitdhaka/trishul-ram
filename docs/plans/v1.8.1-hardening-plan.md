## Objective and boundaries

Close known post-release journal gaps, make capability declarations accurate,
and establish evidence for the existing internal-auth enforcement rollout.
Preserve v1.8.0 delivery tiers, identity fencing, patch compatibility and the
legacy SNMP escape hatch. Keep strict stream rejection and in-memory webhook
202 semantics explicit. No new connectors, AI expansion, RBAC, manager HA,
deeper queues, or execution-runtime redesign in this cycle.

## Implementation sequence

1. Capture the journal/capability contracts and reproducible failure cases.
2. Implement H181-01 and its recovery coverage first; then H181-02/03.
3. Complete H181-04/05 and document enforcement observation/rollback.
4. Reconcile tracking and gather the full release review/gate evidence.

The journal change must preserve acknowledged-result retention and replay
identity. Outbox retries must not create a second logical terminal result.
Do not fix the crash window by deleting unacknowledged outcomes.

## Operations lane: warn → enforce

The default is not changed automatically by this release. Use the existing
deployment procedure: deploy keys to all internal callers, check probe and
network reachability, observe counters over a representative window including
scheduled runs, restart and drain, then enable enforce in the target deployment.
Require zero unexplained warn misses before the flip and zero unexpected
rejects after it. Record observation duration, exclusions, rollout result and
rollback procedure. This is deployment evidence, separate from code completion;
production rollout is not required to fabricate a software release sign-off.

## Cycle-wide release discipline

These rules also apply to v1.8.2 and v1.8.3:

- One release branch and release PR per version; package progress records include
  failure scenario, changed behavior, tests, live evidence and review disposition.
- Start from the preceding released patch. Pin revisions, images, dependencies,
  CPU/memory limits and configured timeouts in campaign records. A later release
  cannot compensate for an unresolved data-integrity blocker in an earlier one.
- Preserve existing YAML/API contracts. Document API, Helm, storage and default
  changes explicitly; a breaking migration belongs in a separately reviewed
  scope. Add environment variables to `.env.example`, deployment docs and Helm
  where applicable. UI changes require screenshots and browser checks.
- For verified connector/finalization gaps, distinguish fixed, already covered
  with evidence, and residual work. Close only delivered scope. New features
  remain unscheduled; do not imply these patches close all 17 issue umbrellas.
- Run meaningful targeted checks while implementing. At release preparation,
  align package/UI/Helm versions and the template image tag, prepare the changelog,
  record self-review and independent review of the full diff, and require all
  11 `scripts/release-gate.sh` checks green (including ≥75% coverage). Full pytest
  runs outside the Codex sandbox; browser smoke uses Node ≥20. Tag only after
  green gates; releases have no calendar deadline that overrides evidence.

## Completion checklist

- [ ] H181-01–06 accepted with linked evidence; no unresolved data-integrity,
  security or mixed-version compatibility blocker.
- [ ] Worker restart proves recovery of a pre-patch stranded completion and
  replay after a post-patch crash without restarting the manager.

Planning alone changes no version, deployment, issue state or release tag.
