## Objective and boundaries

Establish sustained evidence for the existing recovery, drain, admission and
accounting contracts, then fix verified operational defects. Optimize lock
discipline where needed for cancellation/backpressure; speculative codec,
Rust, descriptor-conversion or SQL-pooling projects remain unscheduled.
Use existing API/UI surfaces for accounting corrections; no DLQ browser,
live-log service, new dashboard or broader operations feature set.

## Finite campaign and pass criteria

Freeze scenario/configuration and evidence locations before starting long runs.
Use deployment Python and exact version images with matched CPU/memory, corpus,
sink durability and concurrency. Reuse existing harnesses and V18 fault oracles;
fix gaps in collection rather than interpreting missing telemetry as success.

- Run one 24-hour representative mixed batch/stream soak. Include a stateful
  pipeline, replayable broker input and local/remote sink cohorts. Collect a
  warm-up baseline and periodic resource/accounting checkpoints.
- Exercise each restart/drain/partition/upgrade recovery scenario at least
  three times. Derive and record recovery deadlines from the configured probe,
  reconcile, drain and callback budgets before execution. Fail if a configured
  deadline is breached or a steady state requires manual repair.
- Run a 30-minute overload/slow-sink phase and demonstrate return to baseline
  after removal of pressure. Prove configured count/byte limits hold and
  undelivered outcomes remain retained. Investigate continued RSS/disk growth
  across comparable steady-state intervals; bounded queue counts alone are
  insufficient evidence of bounded memory or retention.
- Use at least five repetitions for affected performance cells; publish
  individual results, throughput, completion p95, CPU-seconds/record, RSS and
  dependency/configuration details. A gain is not required for a verification
  cell. A regression requires explanation and an explicit disposition.
- Require zero unexplained missing records, false-success outcomes or ownership
  violations in replayable/confirmed-delivery cohorts. Report permitted
  duplicates, intentional drops, uncertainty and unreplayable-source limits.

Record failures and repairs in a dated `docs/reviews/` campaign report. Re-run
affected cells after a repair; do not repeat unrelated green cells without a
new concern. This campaign supplements, rather than replaces, the release gate.

## Sequence and completion

1. Freeze the cohort, budgets and telemetry; audit accounting and lock concerns.
2. Apply verified corrections, run short fault checks and review compatibility.
3. Run the finite soak/fault/performance campaign on the final candidate images.
4. Publish results, update runbooks/sizing, and complete release review/gates.

- [ ] H183-01–06 accepted; raw evidence and accounting oracles are linked.
- [ ] Recovery, upgrade and rollback need no manual execution-state repair;
  all configured capacity and lifecycle budgets hold.
- [ ] Existing operations views accurately explain partial/unknown outcomes.
- [ ] Self-review, independent full-diff review and all release checks pass.

## Following the maturity cycle

v1.9.0 retains its planned legacy SNMP removal scope, gated on default-stack
field/wire evidence from the v1.8.x period. Strict stream support, AI expansion,
manager HA, RBAC, new connectors and other capabilities require separate
prioritization after this cycle. Completion does not mean every historical
proposal has been implemented or every umbrella issue can be closed.
